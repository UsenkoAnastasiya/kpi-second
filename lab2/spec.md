# spec.md — Лабораторна 2: вимоги й сценарії (домен «Бібліотека»)

## Намір

Описати, що система бібліотеки робить для користувачів: пошук, видача, повернення, нагадування. Спирається на модель даних з лабораторної 1 (lab1/model/library.mmd).

## Актори

- **User** (узагальнений актор) ← **Reader** (читач), **Librarian** (бібліотекар) — люди.
- **Notification Service** — зовнішня система (email/SMS), яку система викликає для нагадувань.

## Головні цілі

- Reader: знайти книгу, побачити свої видачі.
- Librarian: видати примірник, прийняти повернення, бачити прострочені видачі.
- Notification Service: отримувати запити на сповіщення читачів.

## Зв'язок із моделлю даних (lab1)

Вимоги використовують лише сутності й атрибути з lab1: Book (title, isbn), Author (full_name), BookCopy (status), Reader (email, registered_at), Loan (loaned_at, due_at, returned_at). Нових сутностей не вводимо.

## Критерії прийняття

1. Кожна вимога записана в EARS (WHEN / WHILE / IF…THEN + «система SHALL…»), однозначна й тестована (без «швидко», «за потреби»).
2. Кожна вимога має id `REQ-NN`; кожен сценарій — `S-NN`; кожен use case — `UC-N`.
3. Є ≥2 типи акторів (людина + зовнішня система) і узагальнення акторів.
4. Діаграма має хоча б один `include` і один `extend`.
5. Матриця трасування — багато-до-багатьох; непокриті вимоги/UC позначено й пояснено (≥1).
6. Назви сутностей і атрибутів у вимогах збігаються з lab1 символ у символ.
7. Вимоги EARS не повинні містити вигаданих сутностей поза ER-моделлю ЛР1 (наприклад, Fine) та двозначних слів (наприклад, «швидко»).
8. Кожна User Story повинна містити явно вказані IDs відповідних вимог EARS у дужках.
9. Прийнятні сценарії мають бути розбивками за 3 окремими файлами (loan, search, overdue), а Use Case діаграма повинна мати 9 нумерованих UC із коректними <<include>>/<<extend>>.
